## 一言

2025-11-30 の記事「業務データベース設計の基本(正規化より大切なこと)」の**実践版**。前作は「テーブル設計 = 業務設計」を、ER 図から業務を読み取る形(A社/B社)で説明した。今作は、**実在のアプリで、業務の決めごとが1つずつテーブル設計に落ちていく過程**を見せ、さらに前作の目で、**自分の設計を読み直す**。

## この題材が向いている理由

- リポジトリの文書が、前作の主張と同じ分け方になっている。
  - `docs/overview.md`:**業務(ドメイン)の正**。用語、関係、保存と計算、誰が何をできるか、MVP の範囲。
  - `docs/er.md`:属性・制約・ER 図・テーブルごとの RLS 判定。
  - つまり「業務を先に文章で決め、それを ER に落とす」順序が、文書に残っている。
- 麻雀は多くの読者がルールを知らないので、業務ルールを**言葉で説明する**必要がある。業務設計の説明に向く。
- 設計者が本人なので、「なぜそうしたか」を断定できる(AI との会話ログも根拠にできる)。

## 業務の決めごと → 設計 の対応(`overview.md`、`er.md` で確認したもの)

| 業務の決めごと | 設計への落ち方 |
|---|---|
| 麻雀グループの全員は同等(役割なし) | `community_memberships` に役割列を持たない |
| 退会しても過去の大会結果は残す。再登録は別人 | `profiles` を残し、`auth_user_id` を NULL にする「墓石」。表示名は「退会済みユーザ」。CHECK 制約で利用中と墓石の形を分ける |
| 大会にはグループ外の人(ゲスト)も出る | `tournament_participants` は `user_id` と `guest_display_name` の XOR。部分ユニーク制約 |
| 離脱・除名・退会後も、過去の大会の記録は変えない | 既存行の `user_id` は残し、ゲストへ載せ替えない |
| 大会ごとにルールが違う。四麻と三麻が混在する | 大会ルールを 1:N で持つ |
| 後から既定ルールを変えても、過去の大会の意味は変わらない | 大会作成時に既定ルールを**値コピー**し、コピー元への FK を持たない。試合が紐づいたルールは修正不可(trigger) |
| 局単位の記録は不要 | 半荘(試合)を最小粒度にする。局のテーブルを持たない |
| 賭け麻雀は扱わない | 金額・通貨の列を持たない |
| 大会の順位は集計で出す | 最終順位・最終ポイントは列にせず、都度集計 |
| 入力途中や変則(人数不足など)を許容する | 点数合計が「持ち点×人数」と一致する制約を、あえて持たない |
| 同着の扱いはルールで違う | 上家取り/折半/手動を列挙型で持つ |

## 前作の目で自分の設計を読む(「気になるところ」候補)

前作は「二重持ち」を手がかりに業務パターンを推測した。同じ目で自分の設計を見ると、次が気になる。**いずれも設計理由を `overview.md`、マイグレーション、会話ログで確認してから書く**(確認前は断定しない)。

- `match_results` に、内訳(基本ポイント・ウマ・トビ・焼き鳥・その他・試合個別)と合計 `points` の両方がある。**二重持ち**に見える。手入力の項目があること、レートを掛けること、ルール変更の影響を受けないこと、のどれが理由か。
- `rank` は点数から計算できるのに保存している。「保存時に計算」と書かれている。理由を確認する。
- 「大会修正ポイント」が1〜5の固定の列で、タイトルは大会に、値は参加者に付く。**列を横に並べる**設計の是非(業務が「最大5件」なのか、妥協なのか)。
- `tournament_participants` が、ゲストと「麻雀グループ所属者のゲスト登録」の二重登録を DB で防げず、アプリ制約にしている(`er.md` に記載)。

## 構成案(たたき台)

前作の A社/B社と同じ**出題形式**を使う案:

1. この記事は何か(前作へのリンク、今回は実践版であること)
2. 先に ER 図だけを見せ、「この ER 図から、どんな業務ルールが読み取れるか」を問う(退会、ゲスト、ルールのコピー、局を持たない、など)
3. 答え合わせ:`overview.md` の業務の決めごとと、設計の対応表
4. 設計判断の深掘り(2〜3個に絞る:墓石、値コピー、制約を持たないと決めたもの)
5. 前作の目で読み直した「気になるところ」と、その理由
6. 振り返り(業務の決めごとを文章にしてから設計したことの効果、やり直すなら)
